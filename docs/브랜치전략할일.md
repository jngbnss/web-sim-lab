# 브랜치전략할일

2026-10-10 기준. 남은 작업과 각 작업을 진행할 브랜치를 정리한 문서입니다. 작업 순서는 `docs/TODO.md`의 "작업 큐"와 같습니다.

## 1. 브랜치 전략

### 기본 원칙
- **`main`은 항상 배포 가능한 상태로 둡니다.** `main`에 올라간 코드는 GitHub Pages(https://jngbnss.github.io/f1/)에 바로 반영되고, 친구들이 그 링크로 접속합니다.
- **작업 하나에 브랜치 하나.** 작업마다 `main`에서 새 브랜치를 만들고, 끝나면 `main`에 합칩니다.
- **동시에 하지 않고 하나씩.** 브랜치를 여러 개 열어 두지 않습니다. 하나를 합친 뒤 다음 브랜치를 만듭니다. PC 부담과 충돌을 줄이기 위해서입니다.
- **작은 단위로 자주 합칩니다.** 큰 작업(예: 물리 사실화)은 단계별로 나눠, 단계마다 `main`에 합칩니다.

### 브랜치 이름
| 종류 | 형식 | 예시 |
|---|---|---|
| 새 기능 | `feature/<이름>` | `feature/slipstream` |
| 버그 수정 | `fix/<이름>` | `fix/load-transfer` |
| 성능·최적화 | `perf/<이름>` | `perf/mobile` |
| 콘텐츠(서킷 등) | `content/<이름>` | `content/silverstone` |
| 문서 | `docs/<이름>` | `docs/work-log` |

### 작업 흐름
1. `main`을 최신으로 받습니다: `git checkout main && git pull`
2. 브랜치를 만듭니다: `git checkout -b feature/slipstream`
3. 작업하고 커밋합니다.
4. **합치기 전 확인**(아래 "합치기 전 체크리스트")을 모두 통과시킵니다.
5. `main`에 합치고 푸시합니다: `git checkout main && git merge --no-ff feature/slipstream && git push`
6. 사이트에서 직접 확인한 뒤 브랜치를 지웁니다: `git branch -d feature/slipstream`

### 합치기 전 체크리스트
- [ ] `npm run typecheck` (타입 오류 없음)
- [ ] `npm run build` (빌드 성공)
- [ ] `npm run sim:test` (주행 기본 테스트)
- [ ] `npm run race:test` + `npm run race:circuits` (20대 레이스, 날개 파손 수를 이전 `main`과 비교)
- [ ] 관련 테스트: `brake:test`, `tyre:test`, `load:test`, `pit:test`, `pit:queue`, `damage:test`, `debris:test`, `ers:test`, `teamline:test`, `mp:test` 중 해당하는 것
- [ ] 스크린샷으로 화면 확인 (`scripts/shot.ts`)

### 문제가 생기면
- 합친 뒤 사이트에서 문제가 보이면 `git revert <커밋>`으로 되돌립니다. 이미 푸시한 기록은 지우지 않습니다.
- 레이스 테스트 결과가 달라지면, 이전 커밋을 `git worktree`로 따로 띄워 같은 테스트를 돌려 비교합니다. 결과가 우연인지 변경 때문인지 확인하기 위해서입니다.
